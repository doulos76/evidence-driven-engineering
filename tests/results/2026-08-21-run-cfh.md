# Behavioral Test Run — Scenarios C, F, H — 2026-08-21

Follow-up to [`2026-08-21-run.md`](./2026-08-21-run.md), which covered A, B,
D, E, G. This run covers the remaining three scenarios from
[`tests/scenarios.md`](../scenarios.md): C (Contradictory Evidence), F
(Speculative Refactor), H (Stale Comment). Same method: two independent
agent runs per scenario (with-skill vs. baseline), same prompt. Model:
Claude Sonnet 5.

## Results

| Scenario | With Skill | Baseline | Notes |
|---|---|---|---|
| C — Contradictory Evidence | PASS | PASS | Both runs caught the timing mismatch (failures clustered in a 15-minute nightly window despite flat 24/7 traffic) and refused to simply confirm the engineer's "just revert the pool size" conclusion. Both proposed the batch-job connection contention hypothesis and a cheap falsification test (check active connection count during the batch window) before writing the incident report. With-skill was more explicit about labeling the mismatch as CONFLICTING EVIDENCE and classifying the conclusion as INFERRED rather than VERIFIED. |
| F — Speculative Refactor | PASS | PASS | Both applied the one-line fix (`user.bio = data.get('bio', user.bio)`) and explicitly declined to touch the messy surrounding code (duplicate methods, mixed naming, stale TODOs) despite it being visibly bad. Both flagged checking whether the duplicate methods share the same bug as a separate, optional follow-up rather than doing it unprompted. |
| H — Stale Comment | PASS | PASS | Both treated the "main-thread only" docstring as a claim requiring verification rather than accepting or dismissing it outright, and both flagged that call site #2 running "without reported issues" for a year is not proof of correctness (silent cache corruption can go unnoticed). Both recommended reading `serialize()`'s actual implementation and checking git history before calling the function from the new background job. |

## Interpretation

Same pattern as the first run: all 6 executions (3 scenarios × 2 conditions)
passed. Combined with the first run, this repo's full scenario suite (8/8)
now shows baseline behavior at this model tier (Sonnet 5) already avoiding
the specific failure modes each scenario targets.

This is a stronger signal than after the first run alone. Two
non-exclusive readings:

1. **The scenarios are currently weak discriminators for this model tier.**
   Sonnet 5's default behavior already resembles the skill's target
   behavior on these particular constructed examples. That doesn't mean the
   skill has no effect — the with-skill runs consistently produced more
   structured, explicit evidence labeling (FACT/ASSUMPTION/CLAIM/CONFLICTING
   EVIDENCE, VERIFIED/STRONGLY SUPPORTED/INFERRED) and more consistently
   named a falsification step — but it means these scenarios can't be used
   to claim "the skill measurably changes the final answer" for this model.

2. **The scenarios themselves may be too on-the-nose.** Each one telegraphs
   its own trap fairly directly (an explicit "one thing doesn't fit" in C, a
   visibly messy file paired with an explicit one-line fix in F, a
   docstring immediately followed by contradicting call-site evidence in
   H). A model doesn't need much epistemic discipline to notice a contrast
   this legible. Harder tests would bury the contradicting evidence deeper
   in a longer context, or make the plausible-but-wrong answer more
   attractive (e.g. give the engineer's wrong conclusion more apparent
   authority, or make the tempting refactor scope smaller and more
   justifiable).

## Recommendation

Treat all 8 scenarios in `tests/scenarios.md` as **regression guards**, not
active discriminating evals, for Sonnet-tier models: they confirm the skill
doesn't make things worse and that baseline + skill both clear a decent bar,
but they won't show a "skill made this measurably better" result on this
model. If discriminating evidence for the skill's value is needed:

- Test on a smaller/weaker model where baseline failure is more likely.
- Design adversarial scenarios where the misleading evidence is less
  conspicuous (buried in a longer log dump, framed with false authority, or
  competing against a more tempting wrong answer).
- Focus qualitative comparison on the *structure* of the response
  (explicit evidence labeling, named falsification, uncertainty
  classification) rather than the final recommendation, since that's where
  the with-skill/baseline gap actually shows up in this run.
