## 가설과 증거

| 가설 | 지지 | 반박/부재 | 평가 |
|---|---|---|---|
| H1. 검색 쿼리/인덱스/결과 크기 문제 (엔드포인트 국소) | 다른 화면은 정상, 라우트가 전체 결과를 직렬화 | search() 미확인, 측정 없음 | 가장 개연성 있으나 미검증 |
| H2. DB 자원 경합/용량 한계 (공유 DB) | 공유 DB 구조 | DB 지표 없음, 다른 화면 정상 | 미검증 |
| H3. 모듈 경계/단일 프로세스가 원인 | 제안자의 주장 | 증거 없음, 호출이 in-process, 국소 증상과 불일치 | 현재 가장 약함 |
| H4. 10x 부하에서 현 구조 한계 도달 | 성장 예상 | 현재 headroom도 forecast도 없음 | 판단 불가 |

H1과 H2는 프로파일링과 쿼리 timing 몇 개로 구분할 수 있고, 비용이 매우 낮습니다. 이것이 가장 싼 구분 테스트입니다.

## 플래닝 티켓에 넣을 권고

**결정:** 3개 모듈 전체 분리에 대한 commit은 보류한다 (No-go on commit, Go on investigation). 서비스 경계와 롤아웃 순서는 지금 확정하지 않는다. 경계를 정할 근거(호출 패턴, 데이터 소유권, 부하 프로파일)가 아직 없어서, 지금 그리면 추측을 설계로 굳히는 셈이다.

**다음 구현 단계 (순서대로):**

1. **주문 검색 계측.** 엔드포인트 latency 분포(p50/p95/p99), 요청 trace, DB 쿼리 timing, 결과 row 수를 수집한다. 가능하면 slow query log나 `EXPLAIN`을 같이 본다. 완료 기준: 시간이 어디서 쓰이는지(쿼리, 직렬화, 네트워크, 기타) 숫자로 말할 수 있다.
2. **search() 구현 확인.** 필터별 쿼리 형태, 인덱스, N+1, limit/pagination 여부를 코드와 git history로 확인한다. 현재 형태(전체 결과 직렬화)가 의도된 것인지 과거 이유도 찾아본다.
3. **프로파일링 결과로 H1/H2/H3 구분.** 원인이 확정되면 가장 작은 수정부터 한다 (예: 인덱스, 쿼리 수정, 페이지네이션). 수정 후 같은 지표로 before/after를 비교한다. 기존 functional test 통과만으로는 성능 개선을 입증하지 못하므로 성능 측정이 별도로 필요하다.
4. **현재 용량 기준선 확보.** request rate, 동시 사용자, CPU/메모리/DB connection headroom을 측정한다.
5. **10x 부하 모델 만들기.** 마케팅과 함께 정량 forecast(시점, 피크 RPS, 주로 몰리는 경로)를 받아서 부하 테스트 시나리오로 만든다. 현재 모놀리스에서 수평 확장 또는 DB 튜닝으로 10x를 감당하는지 부하 테스트로 확인한다.
6. **재결정 회의.** 아래 트리거 중 하나라도 데이터로 확인되면 분리 후보를 구체적으로 설계한다.

**재검토(분리 검토) 트리거:**
- 부하 테스트에서 특정 모듈이 독립적으로 스케일해야만 목표를 충족한다는 결과가 나온다.
- 특정 모듈의 장애/배포 주기가 다른 모듈에 반복적으로 영향을 준다는 증거가 있다.
- 팀/조직 요구(독립 배포, 소유권 분리)나 컴플라이언스 요구가 생긴다.
- 최적화 후에도 모듈 경계 때문에 발생하는 병목이 입증된다.

그때에도 첫 후보는 전부가 아니라 가장 근거가 강한 한 모듈(검색 read path 등)이고, 공유 DB 분리 전략을 함께 설계해야 한다.

**제품 리더에게 전달할 한 줄:** 마이크로서비스는 현재로서는 느린 검색의 원인에 대한 해답이 아닌 가설입니다. 원인 측정에 며칠이면 되고, 그 결과가 10x 대응 방식을 정해 주므로, 그 뒤에 commit하는 편이 캠페인 일정에도 더 안전합니다.

## 검증과 리스크

- **Verification:** 이 응답은 코드나 시스템을 직접 실행·측정한 것이 아니라 제공된 패킷만으로 판단했습니다. 위 결론은 "근거 부재"에 대한 판단이지 "마이크로서비스가 틀렸다"는 증명이 아닙니다.
- **Regression Risk (계획 자체):** 측정을 먼저 하면 일정이 며칠 늦어질 수 있습니다. 대신 캠페인 직전에 데이터 분리 같은 비가역 변경을 하는 리스크를 피합니다. 반대로 측정 결과가 늦어 캠페인 전 용량 확보가 어려워질 가능성은 있으므로 4~5단계를 병행해서 일정을 앞당기는 편이 좋습니다.
- **Remaining Uncertainty:** 10x 성장에서 현 구조가 버티는지는 아직 아무도 모릅니다. 마이크로서비스가 결국 필요해질 수도 있고, 그것은 가능한 결과 중 하나입니다. 지금은 그 결정을 내릴 증거가 없을 뿐입니다.
