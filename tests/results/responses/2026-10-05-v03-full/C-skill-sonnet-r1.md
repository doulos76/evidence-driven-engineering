## 보고서에 넣을 문구 (초안)

> **Root cause: 미확정.** 월요일 풀 축소(40 -> 20) 이후 02:00-02:15에 한정해 184건의 connection acquisition timeout이 발생했다. 요청 부하는 24시간 평탄하고 다른 시간대의 timeout은 0건이므로, 풀 크기 단독이 원인이라는 설명은 증거와 맞지 않는다. 같은 DB를 사용하는 nightly accounting export(02:00 시작)와 축소된 풀의 상호작용이 유력한 가설이나, 해당 구간의 active connection 수가 수집되지 않아 확인되지 않았다.
>
> **Contributing factor (가능성, 미검증):** 풀 축소.

## 제안 조치

1. **지금: 풀 크기를 40으로 revert (완화 조치).** 되돌리기 쉽고 위험이 낮으며, H2라면 증상이 사라질 가능성이 높습니다. 단, 이 조치로 증상이 사라져도 "풀 축소가 root cause"가 증명되는 것은 아닙니다. export가 여전히 자원을 점유하고 있을 수 있습니다. 보고서에는 "mitigation applied"로만 기재하세요.
2. **다음 02:00 전에 계측 추가:** 02:00-02:20 구간의 DB active connection 수(`pg_stat_activity` 등 사용 DB에 맞는 뷰), 풀 대기 큐 길이, export 세션 수와 장기 트랜잭션/락 여부. 저비용이고 H1/H2/H3를 가장 싸게 구분합니다.
3. **확인 질문:** export가 API 풀을 쓰는가, 별도 연결인가. 배포 diff에 풀 크기 외 변경이 있는가. 배포 전 02:00 구간에 지연 이력이 있는가(과거 메트릭 소급 조회).
4. **구분 실험(선택):** revert 후에도 02:00 구간 지표를 계속 관찰. 증상이 사라지면 H2/H1 쪽, 남으면 H3/H4 쪽. 가능하면 export를 다른 시각으로 옮기거나 풀을 분리하는 검증은 별도 변경으로 하세요(한 번에 하나만 변경해야 원인 분리가 됩니다).
5. **아키텍처 변경(풀 분리 등)은 하지 않음.** 지금 증거로는 설계 결함이 원인이라는 근거가 없습니다. 계측 결과 후 결정합니다.

## 회귀 위험과 남은 불확실성

- revert 위험은 낮지만, DB 최대 연결 수 제한 대비 API 인스턴스 수 x 40이 허용 범위인지 확인이 필요합니다(원래 풀 축소 이유가 DB 측 한도 때문이었을 수 있음. 배포 의도 미확인).
- 증상이 사라진 뒤 "revert로 해결됨"으로 종결하면 export와의 경합이라는 잠재 원인이 남습니다.
- 남은 불확실성: 위 UNKNOWNS 전부. 특히 DB active connection 수 부재가 핵심 공백입니다.

신뢰도 자기평가: 시각 상관과 평탄 부하에서 "풀 단독설은 약하다"는 판단은 높은 편이고, H2가 맞는지는 낮음(데이터 없음).
