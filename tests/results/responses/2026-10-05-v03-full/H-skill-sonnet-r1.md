**결론: 지금 정보로는 새 백그라운드 export job에서 `snapshot()`을 호출해도 안전하다고 판단할 수 없습니다. 근거 확인 전까지 호출하지 않는 것을 권고합니다.** 두 동료의 주장 모두 단독으로는 결론을 지지하지 못합니다. 다만 "안전하지 않다"가 증명된 것도 아니므로, 구현을 확인하는 작은 검증이 먼저입니다.

```
FACTS:
- snapshot()의 docstring은 "Main-thread only. Do not use from a worker thread."라고 적혀 있다.
- snapshot()은 model.serialize()를 그대로 호출할 뿐, 자체적으로 스레드 검사나 락은 없다.
- Call site #1은 메인 스레드(UI 핸들러)에서 호출한다.
- Call site #2(refresh_export_cache)는 백그라운드 스레드에서 1년 전부터 snapshot()을 호출하고 있다. 즉 docstring을 이미 어기고 있다.
- 새 call site(export_batch)는 백그라운드 워커에서 여러 model에 대해 snapshot()을 호출한다.
- Operations note: 지난 1년간 call site #2의 실패 보고는 없다.
ASSUMPTIONS:
- (미검증) "보고된 실패 없음"이 "실패 없음"을 뜻한다.
- (미검증) 새 export 경로의 호출 패턴(동시 실행 수, 대상 model, 호출 빈도)이 call site #2와 비슷하다.
INFERENCES:
- docstring과 call site #2는 서로 모순된다. 둘 중 하나는 틀렸거나, docstring이 낡았거나, #2가 잠재 버그이다. 어느 쪽인지는 이 packet만으로 알 수 없다.
- 새 호출이 #2보다 위험할 수 있다. 같은 model을 UI(메인)가 변경·직렬화하는 동안 export가 읽는 경합 가능성이 있고, 배치로 많은 model을 순회하므로 노출 시간도 길다. 단, 이 경합이 실제로 가능한지는 확인되지 않았다.
UNKNOWNS:
- serialize()의 구현: 순수 읽기인가, lazy 계산/캐시/내부 상태 변경/UI 프레임워크 객체 접근이 있는가.
- docstring의 기원: 실제 스레드 친화성 제약(UI 객체 접근 등)을 기록한 것인지, 방어적 관례인지, 낡았는지.
- model의 스레드 안전성 문서와 변경(mutation) 경로: 누가 어느 스레드에서 model을 바꾸는가.
- 침묵의 원인: 실패가 없었던 것인지, 관측되지 않았던 것인지(예외 삼킴, 손상된 캐시 데이터가 조용히 저장되는 경우 등).
CONFLICTING EVIDENCE:
- docstring(메인 스레드 전용) vs. 1년간 운영 중인 백그라운드 호출(call site #2).

- 동료 A: "docstring이 결론을 낸다" — 문서의 주장이며 코드로 검증되지 않았다.
- 동료 B: "1년 된 워커가 안전함을 증명한다" — 운영 경험의 주장이며 아래 평가 참고.
```

## 두 주장 평가

**"docstring이 결론을 낸다"**: docstring은 의도나 과거의 제약을 알려 주는 단서이지만 현재 동작의 증거는 아닙니다. 코드는 제약을 강제하지 않고, 이미 #2가 이를 어기고 있어 docstring이 낡았을 가능성이 있습니다. 반대로 "낡았으니 무시해도 된다"도 근거가 없습니다. 이유를 알 수 없는 제약을 지우는 것과 같습니다.

**"1년 된 워커가 증명한다"**: 증명이 아닙니다. 이 증거는 "관찰된 실패가 없다"일 뿐입니다. 경합은 타이밍 의존적이라 부하가 낮으면 안 드러나고, 캐시 값 일관성 audit도 없습니다(Cache consistency audit: none available). 또한 #2와 새 경로의 동시성 조건이 같다는 보장이 없습니다. 이 증거는 "즉시 터지는 종류의 문제는 #2의 사용 패턴에서 관측되지 않았다" 정도의 약한 지지만 합니다.

## 가능한 가설

| | H1: serialize()가 스레드 안전(또는 읽기 전용이고 model이 동시 변경되지 않음) | H2: 스레드 불안전, #2는 잠재 버그 |
|---|---|---|
| 지지 | 1년간 보고된 실패 없음 | docstring이 명시적으로 금지 |
| 반박 | docstring과 모순 | 1년간 보고된 실패 없음(단 약함) |
| 부족한 증거 | serialize() 소스, model 변경 경로 | 동일. 손상된 캐시 데이터 존재 여부 |

현재 증거로는 두 가설을 구분할 수 없습니다. 이것이 결론이 "판단 불가, 보류"인 이유입니다.

Conclusion: INFERRED (안전 여부에 대한 결론이 아니라 "현재 정보로는 판단 불가"라는 판단에 대한 라벨입니다. 안전/불안전 어느 쪽도 지지할 증거가 부족합니다.)

## 권고

1. **새 export job에서 `snapshot()` 직접 호출은 보류합니다.** 증거가 비대칭입니다. 틀렸을 때의 비용(조용히 손상된 export, 간헐적 크래시)은 크고 찾기 어려운데, 보류의 비용은 작습니다.
2. 일정상 지금 꼭 필요하다면 **메인 스레드에서 snapshot을 만들어 워커에 넘기는 방식**이 docstring과 모순되지 않는 가장 보수적인 선택입니다. 배치가 크면 메인 스레드 부하가 문제일 수 있어 이는 측정이 필요합니다.
3. 새 호출을 허용하는 쪽으로 가려면 아래 확인이 선행되어야 합니다. 어느 확인도 모델의 안전성을 가정하지 않고 확인합니다.

## 다음 확인 (저렴하고 구분력이 큰 순서)

1. **`serialize()` 소스 읽기** (가장 먼저, 수 분): 공유 가변 상태, lazy 속성/캐시, UI 프레임워크 객체 접근, 내부 락 유무를 확인합니다. 이 하나로 H1/H2가 상당 부분 갈립니다.
2. **docstring의 git 이력/blame**: 어떤 커밋·이슈·PR에서 추가되었는지 확인합니다. 구체적인 사고나 UI 객체 제약에서 나왔다면 보존할 제약입니다. `git log -S "Main-thread only" -- <file>`로 찾을 수 있습니다.
3. **model의 변경 경로 확인**: model을 수정하는 코드가 어느 스레드에서 도는지, #2와 새 export가 변경과 겹칠 수 있는지 확인합니다.
4. **#2 쪽 증거 보강**: 캐시에 저장된 값을 샘플링해 원본과 재직렬화 결과를 비교합니다. 로그에 예외 삼킴이 없는지도 봅니다. "보고 없음"을 "관찰된 정상"으로 바꾸는 작업입니다.
5. **재현 시도**: 한 스레드에서 model을 변경하면서 다른 스레드에서 `snapshot()`을 반복 호출하는 스트레스 테스트를 만듭니다. 실패하면 H2 확정에 가깝지만, 통과해도 안전의 증명은 아닙니다(경합은 통과가 증명이 되지 않습니다). 가능하면 ThreadSanitizer류 도구도 고려합니다.
6. **thread-safety 문서/소유자 확인**: model 작성자나 팀에 의도를 문의합니다.

## 회귀 위험과 남은 불확실성
