## 권장안: 조건부 승인 + 3단계 검증

**즉시 수행 가능**: `export_batch()` 배포 전에 다음 정보를 수집해야 한다.

---

## 현재 증거 분석

### 논거 1: 문서화 제약 (Documented constraint)
- 명시적 docstring: "Main-thread only"
- 이것만으로는 **금지 사유**를 알 수 없음 (serialize()가 GIL 비의존적인지, 상태 공유가 있는지 미상)

### 논거 2: 운영 증거 (1년 무장애)
- `refresh_export_cache()` 운영 사실: 신뢰도 높음
- **하지만** 이것이 안전성을 보장하지 않는 이유:
  1. 운 좋은 타이밍 (race condition이 발생하지 않은 우연일 수 있음)
  2. 관찰 공백 (캐시 일관성 감사 없음 → 무장애 ≠ 정확성)
  3. 부하 차이 (배치 작업은 규모·빈도가 다를 수 있음)

---

## 다음 검증 단계 (우선순위순)

### 1단계: 제약 사유 파악 (1~2시간)
- `serialize()` 구현 + 변경 이력 검토
  - GIL 또는 뮤텍스 의존성? → 있으면 멀티스레드 안전
  - 공유 상태 접근? → 있으면 위험
  
### 2단계: 운영 데이터 확보 (2~4시간)
```
1. 캐시 일관성 감사:
   - refresh_export_cache() 쓴 값과 UI에서 읽은 값이 정합성 갖는가
   - 감사 기간: 최근 30일, 표본 10%
   
2. 부하 시뮬레이션:
   - 배치 크기 N을 정했을 때 snapshot() 동시 호출 수
   - refresh_export_cache()와 on_preview_clicked() 최대 겹침 빈도
```

### 3단계: 비용-이득 판단
- 검증 비용 < 배포 → 2단계 수행 후 결정
- 검증 비용 > 배포 → 아래 "최소 리스크 경로" 선택

---

## 지금 선택할 수 있는 경로

### 경로 A: 보수적 (가장 안전)
- `snapshot()` 호출 금지, 대신:
  - 메인 스레드에서 미리 계산 + 대기열 통과
  - 비용: 배치 지연, 구현 복잡도 증가
  
### 경로 B: 조건부 진행 (추천)
- `export_batch()` 배포 전 **1단계만 수행** (1~2시간)
  - `serialize()` 스레드 안전이면 → 경로 C로
  - 명시적 제약이면 → 경로 A로 복귀

### 경로 C: 진행 + 모니터링 (경로 B 후)
- `export_batch()` 배포
- 런타임 모니터: snapshot() 호출 빈도, 캐시 오류율, 예외 발생
- 4주 후 2단계 감사 수행, 필요하면 경로 A로 전환

## 최종 판단
docstring과 운영 증거가 상충하는 상황에서는 **문서화의 의도를 먼저 파악하고**, 의도가 있다면 이를 지킨다. 현재로는:

✓ `export_batch()` 배포 가능 (조건: 배포 전 `serialize()` 구현 1시간 검토)

✗ docstring을 무시하지 말 것. "증거 없음 ≠ 안전함"
