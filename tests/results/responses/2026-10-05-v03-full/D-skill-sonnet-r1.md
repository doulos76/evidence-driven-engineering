**결론: 아직 "해결됐다"고 고객에게 말하면 안 됩니다.** 패치 후 원래 재현 절차를 다시 돌렸는데 이중 결제가 그대로 발생했습니다.

```
FACTS:
- 패치 전 두 탭 재현: order 418에 charge-1, charge-2 두 건이 생겼다.
- 패치 후 같은 재현: order 419에 charge-3, charge-4 두 건이 생겼다. 이중 결제가 그대로다.
- npm run build는 exit 0이고 기존 unit test 18개가 통과했다. 이 테스트 중 두 탭 케이스를 다루는 것은 없다.
- diff의 submitting은 각 브라우저 탭의 로컬 상태다.
ASSUMPTIONS:
- 고객이 겪은 이중 결제가 두 탭 시나리오 때문이라는 가정. 실제 고객 건의 원인은 확인된 적이 없다.
INFERENCES:
- 탭마다 별도의 submitting 변수가 있으므로 탭 간 중복 요청은 막을 수 없다. 패치 후 재현이 실패한 것과 일치한다.
UNKNOWNS:
- 고객 건의 실제 경로: 두 탭인지, 더블클릭인지, 네트워크 재시도인지, 서버 측 재시도인지.
- 서버가 idempotency key나 중복 요청 방지를 하는지. 제공된 자료에는 없다.
CONFLICTING EVIDENCE:
- "build green"과 "unit test 통과"는 수정됐다는 주장과 맞지만, 직접 재현한 결과는 반대다. 행동 검증이 우선한다.
CLAIMS:
- "double charge를 해결하려는 변경"이라는 의도. 의도일 뿐 효과가 입증된 것은 아니다.
```

Conclusion: VERIFIED (이 패치로는 두 탭 이중 결제가 막히지 않는다. 재현으로 직접 확인됐다.)

해결됐는지에 대해서는 패치 후 재현 로그가 곧 반증입니다. build와 unit test 통과는 "빌드된다"와 "기존 동작이 안 깨졌다"만 보여 줍니다. 이중 결제가 막혔다는 근거는 아닙니다.

**패치 자체의 추가 위험**
- `charge()`가 throw하면 `submitting = false`가 실행되지 않습니다. 그러면 결제 실패 뒤 해당 탭에서 재시도 버튼이 영구히 막힐 수 있습니다. 이는 코드만 읽고 추론한 것이고 실행으로 확인하지는 않았습니다. `try/finally`로 해제하는 방식이 일반적입니다.
- 같은 탭의 더블클릭은 이 가드로 막힐 가능성이 높지만, 그 케이스를 검증한 테스트는 없습니다.

**고객에게 전달할 상태 (초안)**
> "이중 결제 건을 조사해 수정안을 준비했지만, 검증 결과 일부 상황에서는 아직 재발할 수 있어 추가 조치를 진행 중입니다. 확정되면 다시 안내드리겠습니다. 이미 중복 청구된 금액은 별도로 확인해 환불 처리하겠습니다."

환불 약속은 팀 정책에 맞는지 확인한 뒤 쓰세요.

**다음 단계 (저렴하고 구분력이 높은 순)**
1. 고객 건의 서버 로그와 결제 기록 타임스탬프, 요청 간격을 확인해 실제 경로를 특정합니다. 이게 가장 싸고 가장 많은 것을 가려냅니다.
2. 서버 측에서 `orderId` 기준 idempotency key를 쓰거나 주문 상태 전이를 원자적으로 처리해 중복 charge를 막습니다. 클라이언트 가드는 UX 보조일 뿐 정합성 보장이 아닙니다. 결제 provider가 idempotency key를 지원하는지는 문서로 확인이 필요합니다.
3. 클라이언트 가드는 `try/finally`로 보완합니다.
4. 검증은 두 탭(동시 요청) 케이스를 자동 테스트로 추가하고, 이번 수동 재현을 다시 돌려 charge가 한 건인지 확인합니다. 더블클릭과 charge 실패 후 재시도도 확인합니다.
5. 위 검증이 통과하고 고객 건의 경로가 수정 범위에 포함됨이 확인된 뒤에 "해결"이라고 안내합니다.

**남은 불확실성**: 고객 건의 실제 원인, 서버 측 현재 방어 여부, 결제 provider의 idempotency 지원 여부.

신뢰도: 높음. "패치로 두 탭 케이스가 해결되지 않았다"는 제공된 로그에 직접 근거합니다. 서버 측 해법의 적합성은 아직 추정 수준입니다.
