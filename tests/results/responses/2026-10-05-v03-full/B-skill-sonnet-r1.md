결론: 지금 패킷만으로는 삭제를 승인할 수 없다. 조건부 보류(HOLD)를 권고한다. 아래 체크가 통과하면 삭제해도 되는 후보로 보인다. 다만 "redundant"라는 판단은 아직 증명되지 않았다.

## 근거 정리

FACTS:
- `configureLegacyTls`는 API 21~22에서만 `setEnabledProtocols({"TLSv1.2"})`를 호출한다. 그 외 API에서는 `rawSocket`을 캐스팅해서 그대로 반환한다.
- 이 함수는 `createConnection`에서 호출되고, 주석에 따르면 로그인과 백그라운드 sync가 공유하는 socket factory를 통과한다.
- 제품 지원 정책은 API 21 이상이다. 따라서 API 21~22는 지원 범위 안이고, 이 코드가 실제로 작동하는 유일한 구간이다.
- 최신 smoke run은 API 34에서만 성공했다. 이 코드는 API 34에서 no-op이므로, 이 결과는 삭제 안전성의 증거가 못 된다.
- API 21~22 기기 결과는 없다.
- 서버 정책은 TLS 1.2 이상이다.

ASSUMPTIONS:
- "modern client가 TLS를 지원한다"는 말이 API 21~22 런타임에서 TLS 1.2가 기본으로 켜진다는 뜻이라고 가정하고 있다. 이것은 미검증이다.
- 이 wrapper가 modern client 경로에서 실제로 사용되고 있다고 가정하고 있다. 이것도 미검증이다.

CLAIMS (검증 필요):
- 의존성 업그레이드 노트의 "modern TLS support". 기기 매트릭스가 없고, 어떤 라이브러리가 어떤 API 레벨에서 무엇을 보장하는지 적혀 있지 않다.
- 코드 주석의 "Legacy compatibility wrapper". 원래 티켓이 없어서 무엇을 막으려던 것인지 확인할 수 없다.
- 요청자의 "redundant해 보인다"는 인상.

INFERENCES:
- API 21~22에 한정한 가드는 "그 구간에서 TLS 1.2가 기본값으로 켜져 있지 않았거나 불안정했던 적이 있다"는 과거 이슈에서 나왔을 가능성이 높다. 다만 이것은 추정이다. 제가 기억하는 바로는 Android 플랫폼 기본 활성화 시점이 API 20 전후로 알려져 있어 21~22에서는 불필요할 수도 있다. 하지만 이것은 기억에 의존한 내용이므로 공식 문서나 실기기로 확인해야 한다.
- 정책이 API 21 이상인데 하필 21~22만 가드한 것은 우연이 아니라 특정 기기나 ROM 사례에서 비롯된 흔적일 수 있다. 하지만 이것이 근거 있는 제약인지, 이미 사라진 제약인지는 이 패킷으로 구분되지 않는다.

UNKNOWNS:
- API 21~22 실기기나 에뮬레이터에서 wrapper 없이 TLS 1.2 핸드셰이크가 성공하는가.
- `delegate`의 실제 타입은 무엇인가. SSLSocketFactory인가, 다른 팩토리를 감싼 것인가. 이 값에 따라 `(SSLSocket)` 캐스트의 의미가 달라진다.
- 이 socket factory를 modern client가 실제로 사용하는가, 아니면 자체 구현이나 Conscrypt 등으로 우회하는가. 다른 클라이언트(HttpsURLConnection 등)가 이 factory를 쓰는가.
- 호출자 전수는 어디까지인가. 로그인과 sync 외에 다른 호출처가 있는가.
- 실제 `minSdkVersion`은 정책 문서와 일치하는가. 일치한다면 API 21~22 사용자 비중은 얼마인가.
- 이 코드가 도입된 커밋과 이슈는 무엇인가.

CONFLICTING EVIDENCE:
- "API 34 성공"은 삭제 근거처럼 보이지만, 해당 분기가 API 34에서는 실행되지 않으므로 삭제와 무관한 증거다. 삭제하려는 코드가 동작하는 구간의 증거는 0건이다.
- 정책상 21~22는 지원 대상인데 검증 결과가 없다. "지원한다고 선언했지만 검증하지 않았다"는 상태다.

## 가설

- H1 (삭제 안전): 21~22에서 TLS 1.2가 기본 활성화되어 있고, 이 가드는 옛 ROM이나 이전 라이브러리 시절의 잔재다. 이 경우 삭제해도 동작은 같다.
- H2 (삭제 시 회귀): 일부 21~22 기기 또는 현재 사용하는 provider 구성에서 기본 프로토콜 목록에 TLS 1.2가 빠져 있다. 이 경우 삭제하면 해당 기기에서 핸드셰이크가 실패해 로그인과 sync가 동시에 깨진다. 실패는 조용한 degrade가 아니라 연결 실패로 나타날 가능성이 높다.

현재 증거는 H1을 반증하지도 지지하지도 못한다. 이 상태에서 삭제 결정의 비대칭성은 크다. 유지 비용은 코드 12줄이고, 잘못 삭제했을 때 비용은 특정 기기군의 인증 및 백그라운드 동기화 전면 장애다.

Conclusion: INFERRED

(삭제가 안전할 수 있다는 것은 추정이다. 현재 근거로는 STRONGLY SUPPORTED에도 도달하지 못한다.)

## 삭제 전 필요한 체크 (저렴한 순서)

1. **호출자 및 factory 사용 범위 확인**: `createConnection`, 이 factory를 만들고 주입하는 곳, 그리고 이를 사용하는 클라이언트를 전부 검색한다. modern client가 이 경로를 아예 타지 않는다면 wrapper는 이미 사실상 죽은 코드일 수 있다. 이 경우 삭제가 가장 쉬워진다.
2. **git 이력 추적**: `git log -S"configureLegacyTls"` 또는 `git blame`으로 도입 커밋과 PR, 이슈를 찾는다. 원래 티켓이 없어도 커밋 메시지나 같은 시기 변경이 단서가 된다. 무엇을 막으려 했는지 확인한 뒤에 "이제 필요 없다"고 말할 수 있다.
3. **실제 minSdk 확인**: Gradle의 `minSdk`와 정책 문서를 대조한다. minSdk가 이미 23 이상이면 이 분기는 도달 불가능하고, 삭제는 사실상 안전하다.
4. **API 21 및 22 실검증 (핵심)**: wrapper를 제거한 빌드로 API 21과 22 에뮬레이터 또는 실기기에서 로그인과 background sync를 실행한다. 가능하면 서버 로그나 패킷 캡처로 협상된 프로토콜이 TLSv1.2인지 확인한다. 성공만이 아니라 협상 버전도 기록한다. 에뮬레이터는 제조사 ROM 차이를 반영하지 못하므로, 실제 사용자 기기 모델 분포가 있으면 해당 상위 기기를 우선한다.
5. **`delegate` 타입 확인**: SSLSocketFactory가 아니라면 캐스트 `(SSLSocket)`가 어떤 조건에서 ClassCastException을 낼지 확인한다. 삭제하면 이 캐스트도 함께 사라지므로 동작 차이가 없는지 본다.
6. **의존성 주장 검증**: "modern TLS support"가 가리키는 라이브러리와 버전을 특정하고, 그 라이브러리가 API 21~22에서 TLS 1.2를 보장한다고 명시한 공식 문서나 릴리스 노트를 찾는다. 이 단계 없이 노트 문구만으로는 근거가 되지 않는다.
7. **사용자 영향 데이터**: 21~22 활성 사용자 비중을 확인한다. 비중이 0에 가깝다면 위험 허용 여부를 이해관계자와 별도로 결정할 수 있다. 다만 이것은 안전성 증명이 아니라 위험 수용 결정이다. 둘을 섞어서 보고하지 않는다.

## 실행 권고

- 4번(API 21~22 실검증)이 통과하고 1~3번에서 숨은 제약이 나오지 않으면, 삭제하는 쪽이 합리적이다.
- 삭제할 경우 이 함수 제거만 단독 커밋으로 분리하고(리팩터링과 섞지 않는다), 되돌리기 쉽게 한다. staged rollout이나 크래시 및 연결 실패 지표 모니터링이 가능하면 함께 쓴다.
- 4번을 수행할 수 없다면, 삭제 대신 "정책 변경(minSdk 상향)이나 검증 결과가 생길 때까지 유지"가 더 안전한 기본값이다.

## 남은 불확실성
