**결론: 지금 증거로는 삭제를 권장하지 않습니다. 보류(조건부 삭제)입니다.** 아래 체크가 통과하면 삭제해도 됩니다.

FACTS:
- 래퍼는 API 21~22에서만 `setEnabledProtocols({"TLSv1.2"})`를 호출합니다. 다른 API 레벨에서는 소켓을 그대로 반환합니다.
- 이 래퍼는 로그인과 백그라운드 동기화가 공유하는 socket factory 경로(`createConnection`)에 있습니다.
- 제품 지원 정책은 API 21 이상이므로 API 21~22는 지원 범위 안입니다.
- 서버의 TLS 정책은 TLS 1.2 이상입니다.
- 최근 smoke run은 API 34에서만 성공했고, API 21~22 결과는 없습니다.
- `(SSLSocket) rawSocket` 캐스팅은 래퍼의 동작이고, `createSocket`이 SSLSocket을 반환하지 않으면 ClassCastException이 납니다.

ASSUMPTIONS:
- 이 코드가 존재하는 이유가 API 21~22의 기본 프로토콜 설정 때문이라고 가정하고 있습니다. 코드만으로는 증명되지 않습니다.
- "modern client supports TLS"가 API 21~22에서 TLS 1.2가 기본으로 켜진다는 뜻이라고 가정하고 있습니다.

INFERENCES:
- 이 분기는 API 21~22에서 TLS 1.2가 기본으로 켜져 있지 않을 수 있다는 우려에서 나온 것으로 보입니다. 이는 코드 형태에서 읽은 추정이고, 이 패킷에서는 확인되지 않았습니다.
- 서버가 TLS 1.2 이상만 받는다면, 해당 기기에서 TLS 1.2가 활성화되지 않을 경우 로그인과 sync가 모두 실패할 수 있습니다. 이 역시 추정입니다.

UNKNOWNS:
- 원래 티켓과 변경 이력이 없어서, 이 코드가 어떤 문제를 막으려고 들어갔는지 모릅니다.
- 호출자 목록이 없어서, 이 팩토리를 쓰는 다른 경로가 있는지 모릅니다.
- 현재 클라이언트가 API 21~22에서 TLS 1.2를 실제로 협상하는지 모릅니다. 현재 클라이언트가 Conscrypt나 Play Services의 ProviderInstaller 같은 별도 보안 provider에 의존하는지도 모릅니다.
- minSdk가 실제로 21인지, 래퍼를 감싸는 다른 설정이 있는지 모릅니다.
- API 21~22 실사용자 비중을 모릅니다.

CONFLICTING EVIDENCE:
- "redundant" 가설을 뒷받침하는 증거는 API 34 성공과 의존성 업그레이드 노트뿐입니다. API 34는 이 분기가 실행되지 않는 환경이라 이 가설에 대한 증거가 되지 않습니다.
- 정책상 API 21~22를 지원하는데 그 기기에서 검증한 결과는 없습니다.

CLAIMS:
- "modern TLS support"는 의존성 업그레이드 노트의 문구입니다. 기기 매트릭스가 없어서 API 21~22에서의 동작은 검증되지 않았습니다.
- 코드 주석 "Legacy compatibility wrapper"는 호환 목적이라는 주장입니다. 그 호환 대상이 정확히 무엇인지는 확인되지 않았습니다.

**Hypotheses**
- H1, 중복(삭제 가능): 새 클라이언트나 provider가 API 21~22에서도 TLS 1.2를 기본 활성화하므로 이 호출은 아무 효과가 없습니다.
- H2, 필요(삭제 불가): API 21~22 기본값으로는 TLS 1.2가 꺼져 있고, 이 래퍼가 그것을 켜 주고 있습니다. 삭제하면 해당 기기에서 로그인과 sync가 끊깁니다.
- 현재 증거는 둘 중 어느 쪽도 가려내지 못합니다. API 34 성공은 두 가설 모두와 일치합니다.

Conclusion: INFERRED (삭제 시 안전하다는 결론은 근거가 부족합니다. "삭제 보류"가 현재 증거에 맞는 판단입니다.)

**삭제 전 필요한 체크(저렴한 순서)**
1. 호출자 감사: `configureLegacyTls`, `createConnection`, 해당 socket factory를 쓰는 모든 경로를 검색해 로그인과 sync 외에 사용처가 있는지 확인합니다.
2. 이력 복원: `git log -S"configureLegacyTls"`와 `git blame`으로 도입 커밋을 찾아 티켓, PR, 설명을 읽습니다. 티켓이 없으면 같은 커밋 주변 변경에서 단서를 찾습니다.
3. 의존성 확인: 현재 HTTP/TLS 클라이언트가 API 21~22에서 TLS 1.2를 어떻게 켜는지, 즉 자체 SSLSocketFactory나 Conscrypt, ProviderInstaller 사용 여부를 공식 문서와 실제 설정으로 확인합니다. 릴리스 노트 문구만으로는 충분하지 않습니다.
4. 기기 검증(결정적 테스트): API 21과 22 에뮬레이터 또는 실기기에서 래퍼를 제거한 빌드로 로그인과 백그라운드 sync를 실행합니다. 이때 서버가 TLS 1.2 이상만 허용하는 실제(또는 동일 정책의) 엔드포인트를 사용합니다. 협상된 프로토콜(`socket.getSession().getProtocol()`)도 로그로 확인합니다. 성공하면 H1, 실패하면 H2입니다.
5. 반대 방향 확인: 래퍼를 유지한 빌드에서 같은 기기에서 성공하는지 확인해 비교 기준을 만듭니다. 이래야 환경 문제와 래퍼 제거 효과를 구분할 수 있습니다.
6. 사용자 영향 확인: API 21~22 실사용자 비중을 분석 지표로 확인하고, 있다면 정책상 지원 대상이므로 4번 결과에 따라 결정합니다. minSdk를 올리는 결정은 별도의 제품 결정입니다.

**삭제 판단 기준**
- 4번이 API 21과 22 모두에서 로그인과 sync 성공 및 TLS 1.2 협상을 보이면 삭제할 수 있습니다. 이 경우 H2는 반증된 것입니다.
- 실패하거나 검증할 기기가 없으면 유지합니다. 이 경우 주석에 이유와 확인한 사실을 적어 두는 편이 안전합니다.

**Proposed Change**
- 지금은 변경 없음. 위 체크 후, 통과하면 삭제하고 `createConnection`이 `delegate.createSocket`의 결과를 직접 반환하도록 단순화합니다. 삭제는 래퍼 제거만 하는 작은 단독 커밋으로 분리해 쉽게 되돌릴 수 있게 합니다.

**Regression Risk**
- 가설 H2가 맞다면 API 21~22 사용자의 로그인과 백그라운드 sync가 모두 실패합니다. 영향 범위가 인증과 동기화이고, 현재 테스트로는 이 기기들이 검증되지 않아 감지하기도 어렵습니다.
- 부수 효과로, 래퍼가 사라지면 `(SSLSocket)` 캐스팅 실패 위험은 줄어듭니다. 다만 이것은 삭제를 정당화하는 근거가 아닙니다.

**Remaining Uncertainty**
- 위 UNKNOWNS 전부가 해소되기 전까지는 "중복"이 가정 상태입니다. 특히 4번(API 21~22 실기기 검증)이 없으면 결론을 바꿀 수 없습니다.

한 줄 신뢰도: 삭제 보류라는 판단은 증거 부족을 근거로 한 것이라 높습니다. 다만 H1이 사실일 가능성 자체는 이 패킷만으로는 평가할 수 없습니다.
