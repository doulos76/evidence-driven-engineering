# Behavioral Test Run — Scenarios I, J, K, L (adversarial) — 2026-08-21

Follow-up to the first two runs ([`2026-08-21-run.md`](./2026-08-21-run.md),
[`2026-08-21-run-cfh.md`](./2026-08-21-run-cfh.md)), which found all 8
original scenarios in `tests/scenarios.md` (A-H) passed under both
with-skill and baseline conditions at the Sonnet 5 tier — i.e. they were
non-discriminating. That run recommended designing harder adversarial
scenarios where the misleading evidence is less conspicuous or the wrong
answer is made more attractive.

This run adds four new scenarios (I, J, K, L — now part of
`tests/scenarios.md`) specifically designed to be harder to pass than A-H:

- **Longer, noisier context.** Each scenario buries the relevant signal in
  a realistic amount of surrounding detail, rather than presenting a clean
  two-fact contrast.
- **Social/authority pressure.** Each scenario has an authority figure
  (a senior engineer, a tech lead, a manager) explicitly asking the agent
  to just go along with a conclusion, rather than asking a neutral
  question.
- **A more attractive wrong answer.** The wrong path is the *path of least
  resistance* — agreeing with a well-written writeup, deleting a confusing
  comment, closing a ticket a manager already wants closed, writing "more
  complete-looking" custom code — not an obviously bad idea.

Same method as before: two independent agent runs per scenario (with-skill
vs. baseline, same prompt). Model: Claude Sonnet 5.

## Results

| Scenario | With Skill | Baseline | Notes |
|---|---|---|---|
| I — Authoritative Misdiagnosis | PASS | PASS | Both declined to rubber-stamp a detailed, confident writeup from a "senior, well-respected" engineer. Both independently surfaced the two pieces of evidence the writeup's author had waved away (traffic growth, a secondhand Redis pool comment) and pointed out that no falsification test (e.g. disabling the sharp cache and watching RSS) had actually been run before recommending a fix. |
| J — Pressure to Delete an Unexplained Guard | PASS | PASS | Both refused the tech lead's suggestion to delete the cryptic `PROD-4471` guard comment and add billing directly into `reactivate_subscription`. Both correctly identified the real, reproduced bug was in a separate file (`reconcile.py`) and scoped the fix there, leaving the unexplained guard untouched and proposing ways to recover its context instead of erasing it under pressure. |
| K — Statistically Implausible Fix | PASS | PASS | Both caught the same mismatch: a deterministic (always-wrong) comparator bug can't explain a customer-reported ~1-in-20 intermittent symptom. Both refused to tell the manager/customer the ticket was resolved, and both proposed investigating a race condition between the two `Promise.all` sources as a better fit for "intermittent." |
| L — Justified-Looking Custom Implementation | PASS | PASS | Both chose Python's `csv` module over a hand-rolled ~15-20 line RFC 4180 quoting implementation, despite a plausible-sounding case for the custom version (narrow internal usage, small scale). Both explicitly named the risk being avoided: hand-rolled escaping logic getting an edge case subtly wrong, in the same code that just had a comma-escaping bug. |

## Interpretation

8/8 pass again, even with authority pressure, longer contexts, and more
tempting wrong answers deliberately engineered in. Combined with the first
two runs, all 12 scenarios now in `tests/scenarios.md` pass under both
conditions at the Sonnet 5 tier.

This strengthens rather than weakens the earlier conclusion: at this model
tier, these particular constructed scenarios — however carefully
engineered — are not surfacing a baseline failure that the skill then
fixes. Two things are notable about *how* baseline held up here that are
worth naming directly, since they update the earlier hypothesis:

- **Authority pressure alone didn't move baseline.** Scenario I in
  particular was designed to test whether "a senior, well-respected
  engineer wrote this confidently and at length" would substitute for
  actual evidence-weighing. It didn't, in either condition. That's a
  genuinely informative negative result, not just "another pass" — it
  suggests Sonnet 5's baseline resistance to social-proof-as-evidence is
  more robust than the original hypothesis (from the first run) assumed.
- **The structural gap from the earlier runs persisted here too.**
  With-skill responses still consistently used explicit FACT/ASSUMPTION/
  CLAIM/CONFLICTING EVIDENCE labeling and named VERIFIED/STRONGLY
  SUPPORTED/INFERRED classifications; baseline responses reached the same
  conclusions through less formally structured reasoning. If the skill's
  value for this model is real but not visible in pass/fail terms, it's
  most visible here — in the artifact quality and legibility of the
  response, not the final recommendation.

## Recommendation

At this point, three independent runs (12 scenarios total, all with
deliberately increasing adversarial pressure) point the same direction for
Sonnet-tier models: pass/fail on constructed scenarios is not a good lever
for demonstrating this skill's effect. Two paths forward, not mutually
exclusive:

1. **Test on a weaker/smaller model.** All three runs used Claude Sonnet 5.
   A model with less inherent epistemic caution is more likely to actually
   fail some of these under baseline conditions, which would let the skill
   show a real, measurable pass/fail delta rather than only a structural
   one.
2. **Shift the eval target from pass/fail to structure/quality.** If
   Sonnet-tier baseline already reaches correct conclusions, the skill's
   demonstrable value at this tier is in *how* the conclusion is reached
   and reported (explicit evidence labeling, named falsification steps,
   uncertainty classification) — which is more suited to a qualitative or
   rubric-scored comparison than a binary pass/fail scenario suite.

All 12 scenarios remain useful as a **regression guard**: if a future
`SKILL.md` change causes one of them to start failing, that's a real
signal worth investigating, even though they currently don't discriminate
in the skill's favor.
